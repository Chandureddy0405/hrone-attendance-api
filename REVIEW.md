List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Unconditionally returns `{"status": "ok"}` with 200 without checking database connectivity. OpenAPI requires 200 only if MongoDB answers a ping, else 503. | Stopping MongoDB and requesting `GET /health` returns 200 instead of 503. | Added `db.command("ping")` in a `try...except` block; returns 200 on success, raises `HTTPException(503, ...)` on failure. |
| 2 | Startup lifecycle (lines 22-28) | Fails to create required database indexes on startup. Data model specifies only `_id` is seeded and all indexes must be created idempotently at startup. | Inspecting `db.employees.index_information()` or `db.attendance_logs.index_information()` shows only `_id_`. Concurrency guarantees fail; large scans do full collection scans (COLLSCAN). | Added FastAPI `lifespan` handler that idempotently creates unique and compound indexes (`emp_code`, `(emp_code, date)`, `(department, joined_on)`, `(date, -1, emp_code, 1)`, etc.). |
| 3 | `create_employee` (lines 79-85) | Concurrency race condition using check-then-insert (`find_one` followed by `insert_one`) without relying on a database-level unique constraint. | Two concurrent `POST /employees` requests with identical `emp_code` both pass the check and either create duplicate records or crash with unhandled 500. | Enforced database unique index `{emp_code: 1}`, wrapped `insert_one` in `try...except DuplicateKeyError`, and returned HTTP 409. |

| 5 | `EmployeeIn` / `create_employee` (lines 53-61, 78) | Missing validation for `shift_start != shift_end` and regex formats on `emp_code`, email, and shift times. | Creating an employee with `shift_start == "09:30"` and `shift_end == "09:30"` returns 201 Created instead of 422 Unprocessable Entity. | Implemented Pydantic `@model_validator` ensuring `shift_start != shift_end` (422) and validated regex patterns for `emp_code`, `email`, and 24h `HH:MM`. |

### Examined and Decided NOT to be Defects
1. **`db = client[os.getenv("MONGO_DB", "attendance_db")]` at module scope**:
   - Initial review considered moving database connection into a dependency. However, per problem statement and starter kit architecture ("Put all your code in this one file. It must start with `uvicorn app.main:app --port 8000`"), module-level PyMongo client with a lifespan startup hook is the standard, idiomatic pattern for PyMongo thread-safe client connection pooling across requests.
2. **Storing `date` as ISO string `"YYYY-MM-DD"` instead of BSON date**:
   - Considered whether `date` should be a BSON datetime. `DATA_MODEL.md` explicitly specifies: *"Calendar dates and times of day are plain strings on purpose: a date is not an instant, and turning it into one forces a time zone on it."* Keeping `date` as `"YYYY-MM-DD"` string is an intentional design choice and adhering to it is correct.
3. **Absence of separate `_id` in response models**:
   - In standard CRUD APIs, an `id` field is often expected. Here, `DATA_MODEL.md` explicitly states: `_id is internal and never appears in a request or response. Attendance records have no id either; a record is addressed by (emp_code, date)`. Excluding `_id` is an intentional requirement, not a defect.
